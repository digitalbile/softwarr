# Architecture

This is a map of the code for people changing it. The README covers running softwarr, and `docs/superpowers/specs/2026-11-23-softwarr-design.md` explains why it works the way it does.

softwarr is one Go binary. It serves a JSON API under `/api/v1` and the React UI, which is embedded into the binary from `web/dist`. Data lives in one SQLite file.

## Layout

```
cmd/softwarr/        main: reads config, builds every service, starts the background loops and the HTTP server
internal/            all Go code; nothing here is importable from outside the module
  httpapi/           routes, middleware, and handlers (one file per resource)
  requests/          the request lifecycle: create, approve, grab, poll, import
  library/           library items, file delivery (single file or zip), retention
  auth/              users, passwords, sessions, OIDC
  notify/            in-app notifications and webhooks
  health/            the checks shown on the System page
  settings/          the settings document stored in SQLite
  downloadclient/    the download client interface and registry
    qbittorrent/     the only client so far
  prowlarr/          the Prowlarr search client and release parsing
  importer/          hardlink-or-copy of a finished download into the library
  pathmap/           remote path mappings between a download client and softwarr
  db/                opening the database and running migrations
    migrations/      goose migrations, embedded in the binary
    queries/         SQL that sqlc turns into Go
    dbq/             generated by sqlc; don't edit
  events/            the broker that fans events out to SSE clients
  config/            environment variables
  fsutil/ logbuf/ releasetoken/ torrentfile/ testutil/   small helpers
web/src/             the React UI
```

## How the Go packages depend on each other

Imports go one way, from the top of this list toward the bottom:

1. `cmd/softwarr` builds everything and passes it in.
2. `httpapi` turns HTTP into calls on services.
3. Domain services: `requests`, `library`, `health`, `auth`, `notify`.
4. Building blocks they use: `settings`, `downloadclient`, `prowlarr`, `importer`, `pathmap`, `db/dbq`.
5. Packages with no internal imports: `events`, `config`, `fsutil`, `logbuf`, `torrentfile`.

A package should never import one above it. `requests` sits at the center and imports most of layer 4, so changes to the request flow usually land there.

Services take their dependencies through their constructor, including the clock (`now func() time.Time`) and the `*http.Client`. That keeps them testable without globals. `main.go` is the only place they're wired together, and `httpapi.Deps` is the list of what the HTTP layer gets.

## Request flow

A user searches (`search_handlers.go` calls Prowlarr). Each result carries an encrypted token from `releasetoken`, so the browser never sees download links and can't make up a release. The user requests a release, and `requests.Service` creates the row. An admin approves it, or it's approved automatically.

`requests.Worker` runs every 15 seconds. It sends approved requests to a download client, polls downloads until they finish, then calls `importer` to place the files under the library folder and records the library item. Every state change goes through `requests/state.go`, which lists the allowed transitions.

Changes are published on the `events` broker. `events_handler.go` streams them to the browser over SSE, and the UI refetches the affected queries.

## Conventions

### Handlers

Each resource has a `*_handlers.go` file with a `registerXRoutes(mux)` function, called from `server.go`. Wrap handlers with `requireUser` or `requireAdmin`. Write responses with `writeJSON` and `writeError`, and use `serverError` for anything unexpected, which logs the error and hides it from the client.

Handlers call a service and never query the database, so the rules about what can change stay in one place and can be tested without HTTP. `httpapi.Deps` has no database handle, which keeps it that way. A new resource gets a service or store in its domain package, with a constructor that `main.go` passes into `Deps`.

Each service exports sentinel errors (`ErrNotFound`, `ErrConflict`, and so on). The handler file maps them to status codes in one function, such as `writeRequestError`. Error text that reaches users is written as a full sentence, which is why some error strings are capitalized and end with a period.

### Database

To change the schema, add a migration in `internal/db/migrations` with the next number and both `-- +goose Up` and `-- +goose Down` sections. Numbers are sequential, so if `main` gains a migration with the same number while your branch is open, renumber yours before merging.

To add or change a query, edit the `.sql` file in `internal/db/queries` and run `make generate`. Commit the regenerated `dbq` files. CI runs `sqlc diff` and fails if they're out of date.

### Download clients

A client implements `downloadclient.Client` and registers itself from an `init` function with `downloadclient.RegisterNamed`. Add a blank import for the package in `cmd/softwarr/main.go`. Clients add and read downloads only; they never pause, remove, or recategorize anything.

### Tests

Go tests sit next to the code. `testutil.NewDB` gives a test its own migrated SQLite database. HTTP tests use the helpers in `httpapi/testserver_test.go`, and outside services are faked with `httptest` servers.

UI tests use Vitest, Testing Library, and msw. Call `setupApiServer()` at the top of a test file, then override routes per test with `server.use`. The default handlers are in `web/src/test/server.ts`.

## Frontend

```
web/src/
  api/         fetch wrapper (client.ts) and the API types (types.ts)
  auth/        the signed-in user, and route guards
  events/      the SSE subscription that refreshes queries
  layout/      the app shell and notifications bell
  pages/       one component per route; admin/ and settings/ hold those sections
  components/  pieces shared by more than one page
  test/        msw server and render helpers
```

Server data goes through TanStack Query. Components come from Mantine.

`api/types.ts` is written by hand to match the Go JSON types. When you change a response in Go, change the type there in the same pull request.

## Checks

Run `make lint` and `make test` before pushing. CI runs these:

- `go vet`, `go test`, `go mod tidy -diff`, and `sqlc diff`
- golangci-lint, configured in `.golangci.yml`, which also checks gofmt and goimports formatting
- Biome for the UI (`npm run lint`), configured in `web/biome.json`. `npm run format` fixes formatting and import order.
- The UI tests and build, and `make smoke` against the Docker image

`golangci-lint fmt` fixes Go formatting and import grouping.
